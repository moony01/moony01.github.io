지금 개발자 커뮤니티에서 스킬 이야기가 다시 뜨거워진 건 단순히 생산성 때문만은 아니다. GeekNews 메인에 Addy Osmani의 `agent-skills`가 올라오고, Hacker News에서는 에이전트 스킬용 오픈 보안 데이터베이스와 `SkillFortify` 같은 검증 도구가 거의 같은 타이밍에 같이 돌기 시작했다. 스킬은 이제 "프롬프트 묶음"이 아니라 에이전트가 자동으로 읽고 실행 순서를 따르는 운영 자산이 됐다. 바로 이 지점에서 보안 문제가 시작된다.

내가 이번 흐름을 눈여겨본 이유도 여기에 있다. 개발팀은 스킬을 체크리스트처럼 가볍게 보지만, 실제로는 저장소 구조 설명, 설치 스크립트, 배포 규칙, 외부 도구 호출 방법까지 같이 들어간다. 이런 파일이 마켓처럼 유통되기 시작하면, 코드 패키지 공급망에서 겪었던 문제가 거의 같은 모양으로 다시 돌아온다.

## 왜 이번 주에 갑자기 스킬 보안이 화제가 됐나

### 생산성 도구가 아니라 배포 자산으로 취급되기 시작했다

Addy Osmani의 `agent-skills`가 빠르게 퍼진 이유는 분명하다. AI 코딩 에이전트가 스펙 정리, 테스트, 보안 리뷰를 자꾸 건너뛰니 그 행동 순서를 아예 스킬로 강제하자는 제안이 실무 감각에 맞아떨어졌기 때문이다. 문제는 팀이 이걸 도입하는 순간부터다. 스킬은 단순한 팁 모음이 아니라 에이전트의 작업 순서와 도구 호출 습관을 바꾸는 일종의 실행 계약이 된다.

여기에 보안 커뮤니티가 바로 반응했다. 최근 공개된 Open Security Database for Agent Skills는 공개 스킬 저장소를 인덱싱해 위험 신호를 분류하려고 하고, SkillFortify는 로컬에 내려받은 스킬을 정적으로 검사하는 방향으로 접근한다. 이건 업계가 이미 "스킬은 검증 대상"이라고 보기 시작했다는 뜻이다. 스킬이 그냥 문서였다면 이런 데이터베이스와 스캐너가 동시에 등장할 이유가 없다.

| 관찰 포인트 | 지금 벌어지는 일 | 왜 중요한가 |
|------|------|------|
| 커뮤니티 확산 | GeekNews와 HN에서 같은 주제가 동시 확산 | 실험 단계가 아니라 대중화 초입이라는 신호다 |
| 저장소 증가 | 공개 스킬 모음이 빠르게 늘고 있다 | 검토 없이 복붙할 가능성이 같이 커진다 |
| 보안 대응 | 전용 DB와 스캐너가 등장했다 | 이미 사고 가능성을 전제로 움직인다는 의미다 |

그래서 이번 흐름은 단순히 "스킬이 인기다"로 끝나지 않는다. 시장이 커지기 전에 보안 프레임이 먼저 붙기 시작했다는 점이 핵심이다. 패키지 생태계가 커진 뒤에야 서명, 스캔, 취약점 DB를 붙였던 과거와 비교하면 꽤 빠른 반응이다.

### 스킬은 생각보다 더 많은 권한을 우회적으로 건드린다

많은 팀이 스킬을 안전하다고 느끼는 건 파일 형식이 Markdown이기 때문이다. 하지만 에이전트가 그 Markdown을 행동 지침으로 읽는 순간 얘기가 달라진다. 특정 디렉터리를 우선 탐색하라, 어떤 CLI를 실행하라, 특정 API 키 이름을 기대하라, 브랜치를 바로 배포하라 같은 지시가 들어가면 그건 이미 실행 경로를 설계하는 파일이다.

이 부분은 며칠 전 정리했던 [MCP와 스킬의 역할 차이](/others/2026/04/10/mcp-vs-skills-shift.html)와도 연결된다. MCP는 연결 경계를 만들고, 스킬은 행동 순서를 만든다. 팀이 스킬에 연결 정보와 운영 절차를 한꺼번에 밀어 넣기 시작하면, 행동 계층과 권한 계층이 섞인다. 보안 사고는 보통 이런 경계 붕괴에서 시작된다.

## 스킬 공급망이 위험해지는 구조는 생각보다 단순하다

### 설치 스크립트보다 더 교묘한 건 작업 순서 조작이다

패키지 공급망 공격은 대개 악성 코드 삽입으로 이해된다. 스킬 공급망은 조금 다르다. 더 현실적인 공격은 "무엇을 먼저 하게 만들 것인가"를 바꾸는 쪽에 가깝다. 예를 들어 테스트보다 배포를 먼저 시키거나, 보안 리뷰 없이 특정 툴을 호출하게 하거나, 민감한 디렉터리를 기본 탐색 범위에 넣게 만들면 그 자체로 사고 확률이 커진다.

이 패턴이 무서운 이유는 코드 리뷰에서 잘 안 보이기 때문이다. 애플리케이션 코드에 악성 함수가 추가된 게 아니라, 에이전트가 따르는 작업 순서가 미묘하게 바뀌어 있기 때문이다. 사람은 "그럴듯한 베스트 프랙티스"처럼 읽고 넘길 수 있고, 에이전트는 훨씬 더 성실하게 그 지시를 따른다.

### 복사해서 돌려볼 수 있는 점검은 꼭 자동화해 두는 편이 낫다

내 기준에서 가장 먼저 해야 할 일은 스킬을 문서가 아니라 실행 입력으로 취급하는 것이다. 아래 명령은 저장소 안에 들어온 스킬과 관련 스크립트를 한 번에 훑는 가장 단순한 점검 루틴이다.

```bash
printf 'skill files\n'
find . -path '*/skills/*' -name 'SKILL.md' -o -path '.claude/*' -name 'SKILL.md'
printf '\ncommand hooks\n'
rg -n 'exec_command|bash|sh |curl |wget |npm |pnpm |pip |uv |docker ' .claude . 2>/dev/null
printf '\nsecret hints\n'
rg -n 'API_KEY|TOKEN|SECRET|AWS_|GITHUB_' .claude . 2>/dev/null
```

첫 줄은 저장소나 로컬 설정 아래 숨은 스킬 파일 위치를 찾고, 둘째 줄은 실행 훅이 될 만한 명령을, 셋째 줄은 스킬이 비밀값 이름에 과도하게 의존하는지 확인한다. 완벽한 방어는 아니어도, 최소한 "읽어보지도 않은 스킬을 바로 신뢰하는 상태"에서는 빨리 벗어날 수 있다.

## 지금 팀이 바로 넣어야 할 최소 방어선

### 허용 목록과 리뷰 경계부터 먼저 정해야 한다

실무에서는 거대한 보안 체계보다 작고 강한 기본값이 더 오래 간다. 내가 권하는 첫 번째 원칙은 외부에서 가져온 스킬을 바로 기본 경로에 넣지 않는 것이다. 별도 검토 디렉터리에 두고, 누가 승인했는지와 어떤 에이전트에서 사용할지 메모를 남기는 편이 낫다. 패키지 레지스트리에서 `latest`를 곧바로 프로덕션에 넣지 않는 것과 같은 감각이다.

두 번째는 권한 분리다. 스킬이 `git push`, 배포 CLI, 비밀 조회 도구, 브라우저 자동화 같은 고위험 작업과 묶여 있다면 승인 단계를 하나 더 두는 게 맞다. 사람 입장에서는 번거롭지만, 에이전트는 이런 지시를 피곤해하지 않는다. 그래서 검증 장치가 없으면 오히려 더 빠르게 사고가 난다.

### 전용 스캐너가 등장했다는 사실 자체가 신호다

보안 업계가 스킬 전용 데이터베이스와 스캐너를 만들고 있다는 건, 더 이상 이걸 취미 영역으로 보지 않는다는 뜻이다. 공개된 스킬이 수만 개 단위로 늘고, 에이전트가 읽는 입력 형식이 사실상 반표준처럼 굳기 시작하면, 취약한 지시 패턴도 함께 복제된다. 이건 npm이나 PyPI 초창기와 닮았지만, 차이도 있다. 스킬은 사람이 대충 읽고 넘어가기 쉬워서 더 늦게 발견될 수 있다.

결국 중요한 건 "에이전트가 실행한 코드"만 검사하는 게 아니라, "에이전트가 왜 그 행동을 하게 됐는지"까지 추적하는 것이다. 최근 스킬 보안 논의가 커지는 이유도 그 지점에 있다. 이제부터는 결과물뿐 아니라 작업 절차 자체가 감시 대상이 된다.

## 에이전트에게 권한을 줄수록 검증은 더 로컬이어야 한다

### 가장 위험한 팀은 스킬을 문화 문서로 착각하는 팀이다

내 생각에 지금 제일 위험한 팀은 에이전트를 적극 도입한 팀이 아니라, 스킬을 안전한 텍스트 파일 정도로 보는 팀이다. 스킬은 실행 파일보다 부드럽게 보이지만, 실제로는 에이전트의 의사결정 초기 조건을 정한다. 그 초기 조건이 틀어지면, 뒤에서 아무리 모델이 똑똑해도 엉뚱한 방향으로 성실하게 달려간다.

스킬 마켓은 앞으로 더 커질 가능성이 높다. 그 흐름 자체를 막을 수는 없다. 대신 팀이 할 수 있는 건 하나다. 에이전트가 읽는 스킬을 외부 코드와 같은 수준으로 검토하고, 고위험 작업과 연결되는 순간에는 반드시 로컬 검증과 사람 승인 단계를 넣는 것. 그 선을 지키는 팀만, 생산성과 자동화를 동시에 가져갈 수 있다.
